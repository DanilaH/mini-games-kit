# Что переносим из Sudoku Doku 0.17

Дата: 2026-10-23. Статус: ТЗ на перенос и проверенные практики; новых runtime API этот документ не добавляет.

Источник: [DanilaH/sudoku-doku](https://github.com/DanilaH/sudoku-doku), runtime `f97cc1ed1c32e7d2f438fbaea6671530b1a5fc59`, тесты `664e982c1321d9df1ea5e4da1678ab34281b2667`.
Сравнение с mini-games-kit: `43913152e5b409cdb84515eabb69166f6caaa8bb`.
Все пути Sudoku ниже относятся к указанным ревизиям. [Исходное дерево](https://github.com/DanilaH/sudoku-doku/tree/f97cc1ed1c32e7d2f438fbaea6671530b1a5fc59), [проверки](https://github.com/DanilaH/sudoku-doku/tree/664e982c1321d9df1ea5e4da1678ab34281b2667/tests).

## Решение

Сохраняем знания сейчас, извлекаем небольшие механизмы по очереди. Не переносим целиком App.tsx, State, CSS или нативный плагин. Kit должен работать без React, Capacitor и судоку; Android-интеграция подключается отдельно. Числа 1800, 600, 3 подсказки, 5 минут, пороги медалей и дизайн остаются настройками игры.

| Практика | Что уже есть в kit | Добавление из Sudoku | Форма |
| --- | --- | --- | --- |
| Сохранения без гонок | JsonStorageRepository, StorageAdapter | Объединение ожидающих снимков по revision | Малый opt-in модуль + тесты |
| Надёжная награда | DurablePendingTransactionSession, YandexAdsAdapter | Нативный журнал receipt, выдача до ack, восстановление | Контракт + отдельный адаптер |
| Баннер в двух ориентациях | Viewport runtime, safe-area math | Связь DOM-слота с нативной геометрией и реальным размером SDK | Android-рецепт + геометрические проверки |
| Необязательный профиль | Yandex Player Data mirroring | Изоляция guest/account, явный вход, перенос гостевого прогресса | ТЗ и затем независимый coordinator |
| Дейлики и коллекция | RNG primitives | Версионированное расписание, постоянные ID, следующий доступный уровень | Чистые функции с пользовательским каталогом |
| Статистика и трофеи | Нет соответствующего доменного модуля | Дедупликация результатов, время по сессиям, общий/частный прогресс | Сначала правила и тестовые примеры |
| Повторное открытие помощи | Нет | Бесплатное повторное объяснение той же позиции | Чистая политика ключей/учёта |
| Компактный UI | Layout + onboarding playbooks | Главное меню, результат, адаптация управления, пустые состояния | UX-рецепты, не универсальные компоненты |
| Проверка релиза | Yandex build audit | Android process death, upgrade, ads geometry, подпись | Отдельный Android release playbook |

## 1. Очередь снимков — первый кандидат для кода

Источник: `src/platform/storage.ts` (SaveQueue). Сейчас каждый write в JsonStorageRepository имеет значение; нельзя молча заменить его поведение объединением.

Предложение: отдельная очередь revision-снимков поверх StorageAdapter. Игра передаёт revision, сериализацию/валидацию, ключ. На входе фиксируется независимый снимок. Один writer на ключ; межвкладочную синхронизацию очередь не обещает.

Гарантии:
- Уже начатая запись завершается; среди ожидающих полных снимков сохраняется самый новый.
- Promise пропущенного промежуточного снимка завершается только после сохранения более новой замены; ошибка этой записи отклоняет всех её ожидающих callers.
- committedRevision обновляется только после успеха. Последующая запись может восстановить работу после ошибки.
- flush ждёт хвост, существовавший на момент вызова; не означает бесконечное ожидание будущих записей.
- Неверная revision отвергается. Для одинаковой revision нужен явный контракт: это один и тот же снимок; конфликт должен выявляться либо запрещаться API.
- Очередь не подходит для событий, инкрементов валюты и других операций, которые нельзя пропускать.

Проверки: медленная revision 1 + очередь 2/3; обратный порядок; ошибка диска и повтор; мутация объекта после enqueue; одинаковые revision; reload; flush во время активной записи. Внутренняя оптимизация Sudoku saveLocal доверяет immutable reducers — это не безопасный default публичного API.

## 2. Rewarded: журнал → сохранение награды → подтверждение

Источники: `src/platform/index.ts`, `src/core/hint-credits.ts`, `DokuNativePlugin.java`, `tests/reward-transition.test.ts`, `tests/hint-credits.test.ts`.

Переносимый протокол:
1. SDK подтверждает получение награды; закрытие рекламы само по себе ничего не выдаёт.
2. Нативный слой сохраняет receipt с transaction ID и адресатом до уведомления JS.
3. JS проверяет адресата и идемпотентно применяет награду, сохраняет состояние.
4. Только после успешной записи подтверждает receipt через ack.
5. После перезапуска читает неподтверждённый receipt и повторяет шаги 3–4.

Для kit адресат должен включать профиль и игровую сессию/назначение, а не просто gameId. Не выдавать награду новому пользователю при переключении аккаунта. Повтор callback + result, поздний callback и recovery не должны начислять повторно. Переключение профиля должно ждать завершения транзакции либо сохранять её адресность.

Сочетать с существующим DurablePendingTransactionSession; не писать второй общий transaction engine. SDK receipt — внешний факт, его нельзя самостоятельно сгенерировать вместо onRewarded. Проверка SDK и политика начисления остаются разными слоями.

Ограничение источника: native onRewarded при неуспехе commit журнала пишет диагностику и всё равно уведомляет JS. Это не гарантия сохранности при немедленном завершении процесса. При переносе отдельно определить и проверить деградацию при отказе журнала; не рекламировать exactly-once при любом сбое диска. Последний receipt в Sudoku также не является универсальным реестром всех когда-либо обработанных наград.

Приёмка: дубли и неправильный адресат; раннее закрытие/no fill; ошибка save без ack; успешный save + ошибка ack; process death до и после save; ошибка журнала; перезапуск с receipt для завершённой/удалённой сессии (явная политика игры); cleanup listeners.

## 3. Нативный баннер и раскладка

Источники: `src/style.css`, `src/App.tsx`, `BannerPlacement.java`, `DokuNativePlugin.java`, `OfflineGameTest.java`, `tests/browser/visual-refresh.spec.ts`.

Удачный принцип: интерфейс резервирует измеренный слот; баннер не накрывает доску. В portrait слот снизу, в коротком landscape — под управлением рядом с доской. Это пример раскладки, не единственно допустимое положение.

ТЗ адаптера: получать прямоугольник DOM-слота, сообщать фактический размер SDK, явно преобразовывать CSS px/native coordinates, обновляться после rotation/insets/resize, скрываться при уходе с нужного экрана и освобождать observers/listeners. Не создавать бесконечный цикл измерение → resize → измерение. Согласовать резерв при loading/no fill/retry: слот не должен выглядеть случайной цветной полосой или вызывать прыжки управления.

Запреты по опыту: не обрезать игровую область overflow ради рекламы; не отключать рекламу по произвольному порогу высоты; не использовать transform-анимацию предка, меняющую систему координат fixed-слота.

Приёмка: portrait 320×568, landscape 568×320, обычный телефон, планшет, desktop; большие insets; увеличенный рекламный слот; no fill; rotation с загруженным баннером. Проверять пересечение с самой доской, кнопками и границами экрана, а не только контейнером. В эмуляторе отдельно показать реальный demo SDK banner в обеих ориентациях. Мок прямоугольника не доказывает реальный показ.

## 4. Гость, профиль, облако

Источники: `src/platform/accounts.ts`, `adapter.ts`, `rustore.ts`, `src/core/profile.ts`, `tests/profile.test.ts`, `tests/yandex/platform.spec.ts`.

Удачные решения: игра работает без входа; интерактивный login только по действию пользователя; профиль и прогресс отделены от устройства; гость/account A/account B имеют отдельные данные; после переноса гостя в аккаунт гостевое хранилище очищается по явной политике, чтобы не переносить один прогресс в разные аккаунты.

Не копировать PlatformAdapter как готовый универсальный интерфейс: он зависит от Native и import.meta.env. Использовать независимые capabilities (accounts/cloud/ads/banner) и внедряемые адаптеры, без импортов Android в browser core. Не разрастать это до service locator.

Приёмка: offline guest; отказ login; A→guest→B; незавершённый save при logout; облако недоступно; повтор sync; ошибка записи при connect; проверка identity перед каждым remote read/write. UI не обещает облако, когда capability отсутствует.

RuStoreProfiles в исходнике — предусмотренная, но не реализованная нативная граница. Не маркировать RuStore cloud/auth как готовое решение. YandexMirroredStorageAdapter сам по себе не решает изоляцию аккаунтов и merge политики.

## 5. Дейлики, банк и следующий шаг

Источники: `src/core/daily.ts`, `bank.ts`, `progress.ts`, `trophies.ts`.

- Постоянный content ID, отдельно session ID и daily date; перепрохождение не увеличивает уникальный прогресс банка.
- Дейлики имеют отдельное расписание и версию. Опубликованное date→content соответствие не меняется при обновлении; сохранённая сессия имеет приоритет.
- Размер каталога, сложности и пороги наград задаёт игра. Ни 1800, ни 3 сложности не зашивать в kit.
- Определить источник календарной даты (в Sudoku локальная дата), доступность будущих дней, диапазон архива и конец каталога. Локальные часы не дают защиты от читов.
- Следующая задача открывается с результата напрямую. Поиск учитывает завершённые даты и конец каталога; когда задач больше нет, показывается понятное завершение.
- Приёмка: високосный февраль, граница года, timezone/DST, откат часов, последняя дата, полностью пройденный каталог, обновление банка, сохранённый старый daily.

Сид не доказывает уникальность и решаемость. В Sudoku используется подготовленный каталог, а не бесконечная гарантия разных задач на любую дату. Генератор/валидатор задач принадлежит конкретной механике.

## 6. Честная статистика и помощь

Источники: `src/core/activity.ts`, `progress.ts`, `profile.ts`, `hint-credits.ts`, `game.ts`.

Общие и по сложности показатели вычислять из одного набора фактов. Для уникального прогресса — distinct content IDs в нужном каталоге. Для сыгранных партий — session IDs. Для daily — отдельный ключ даты. Подписывать период трофеев и его знаменатель (например, выбранный год /12).

При merge повторная синхронизация не удваивает результаты и время: Sudoku объединяет результаты по ID/дате и берёт максимум времени на сессию. Это политика, не универсальный merge: параллельная игра одной сессии на двух устройствах может требовать иного разрешения. Нельзя выбирать весь профиль просто по большей revision: revisions разных устройств несопоставимы как глобальные часы.

Повторное объяснение одной позиции бесплатно, включая reload; первое открытие уже считается помощью, даже если игрок вручную вписал ответ. Применение открытого объяснения не считает его второй раз. Ключ позиции и версия алгоритма — ответственность игры; формат из 81 цифры не переносить. Кэш Sudoku ограничен 512 позициями, поэтому вечную бесплатность всех исторических позиций он не гарантирует.

Приёмка: повтор merge, повторное прохождение, разные сложности, незавершённая игра, помощь вручную, reload/undo к открытой позиции, ноль кредитов + уже открытое объяснение, переполнение кэша. Политику конфликтов проверять отдельно от инфраструктуры хранения.

## 7. UX-рецепты

- Главное меню даёт явный старт/продолжение, отдельный daily, краткий прогресс и доступ к профилю. Декоративная доска не выглядит доступной для игры.
- Использовать доступную высоту экрана и отдельную landscape-композицию; не оставлять всё содержимое в верхней трети.
- Цель «без скролла» для главного меню не превращать в обрезание текста: при увеличенном шрифте/экстремальном viewport доступность важнее запрета scroll. Архив и статистика могут скроллиться.
- На результате главный следующий шаг виден прежде подробностей; завершённая доска вторична на тесном экране.
- Показывать управление для доступного способа ввода, а не только по OS/user agent: мобильная клавиатура и desktop touch возможны.
- «Календарь» и другие действия имеют признаки кнопки. Цвет медали не единственный индикатор статуса. Проверять contrast в обеих темах, focus, touch targets, reduced motion.
- Профиль сначала показывает имя и достижения; редактирование имени — отдельное действие. Не дублировать всю статистику в каждом экране.
- Пустые состояния объясняют следующий шаг; недоступная реклама не блокирует основную игру.

React-компоненты и CSS Sudoku остаются reference, не новым обязательным skin kit.

## 8. Релизный рецепт Android

Источники: `.github/workflows/release.yml`, `project.yml`, `upgrade-check.yml`, Android instrumented tests, `docs/UI_REFRESH_17.md`.

Сохраняем: отдельный application ID для demo APK; demo ads отдельно от production IDs; приватная подпись; проверка сертификата при обновлении; versionCode; хеш итогового артефакта; offline/save/Back/process-death/rotation проверки; upgrade со старым save без удаления приложения.

Секреты подписи не попадают в репозиторий, логи и тестовые APK. Размер релиза измеряется по release APK, а не debug. Нужны отчёты, какая сборка и какие ad units проверялись.

Доказательства Sudoku 0.17: 43 unit, 26 browser, 4 Yandex scenarios; Android offline/save, restoration, Back, slot geometry и online orientation probes. Реальный demo banner показан portrait/landscape, rewarded/interstitial загружены. Это не подтверждение боевого fill, полного rewarded playback на физическом телефоне, успешного RuStore cloud или роста retention/дохода.

## Порядок реализации и готовность

1. Сохранить этот документ и связать с API index (данный проход).
2. Извлечь opt-in revision snapshot queue: отдельная API-документация, focused tests, без изменения JsonStorageRepository по умолчанию.
3. Описать и реализовать receipt adapter поверх существующих transaction primitives; сначала failure matrix, потом Android integration example.
4. Добавить Android banner recipe и исполняемые geometry/orientation проверки в отдельный пример; SDK не нужен потребителям browser-only kit.
5. На первом реальном потребителе (например, «Семечки») отделить account orchestration и calendar/catalog selectors. Не переносить Sudoku state/merge/codec как общий формат.
6. Переиспользовать UX/release checklist сразу; библиотечные UI компоненты создавать только при реальном совпадении потребностей.

Каждый кодовый перенос фиксирует source revision, отличия семантики, import path, пример использования, lifecycle/cleanup, non-goals и тесты. Новый модуль готов после интеграционного прогона хотя бы одного потребителя, а не после компиляции изолированного куска. Текущий документ не означает, что эти модули уже реализованы.
