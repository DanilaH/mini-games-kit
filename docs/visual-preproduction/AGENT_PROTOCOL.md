# Контракт для агента: визуальное предпроизводство

**Задача агента — предоставить владельцу осмысленный выбор до массовой разработки графики.** Не выбирать окончательный арт-стиль от имени владельца, не производить десятки ассетов до согласования, не подменять макеты рекламными key arts.

## Вход

Получить или самостоятельно восстановить:
- game idea, core loop, rule/UI constraints, режимы и платформы;
- действующие ограничения и уже принятые решения в репозитории; commit SHA;
- 3–6 профильных референсов и их доступные источники (real gameplay vs promotional);
- требования к рекламе, сохранениям, локализации, orientation, производительности и бюджету;
- неизвестные ограничения помечать UNKNOWN, не выдумывать рынок, возраст и бюджет.

Если механика ещё не опробована, сначала показать **нейтральный функциональный wireframe/прототип**. Концепты мира не должны задерживать проверку базового действия.

## Какова последовательность действий

### Step A — короткий product/visual brief

Одна страница: для кого (если известно), что игрок делает, ожидаемая эмоция, исходные арт-предпочтения, предметный словарь, ограничения, три visual pillars и anti-goals.

Пример pillars:
- «Игровое поле занимает визуальный приоритет; персонаж не появляется во время хода».
- «Крупная форма предмета узнаётся при 55px».
- «Победа — короткое материальное ощущение, не длинная катсцена».

### Step B — evidence-based reference teardown

Таблица из референсов с точным URL/снимком/датой; что показано, что лишь заявлено, какие механики/экраны сопоставимы. Отдельно gameplay, menu/meta, icon/marketing, motion.

### Step C — намеренно разные полноценные концепции

По умолчанию **три**: gameplay-first, тематический, смелая отличительная художественная гипотеза. Для маленькой игры допустимы два. Не более четырёх без обоснования.

Для каждой концепции заполнить [CONCEPT_PITCH_TEMPLATE.md](CONCEPT_PITCH_TEMPLATE.md) с:
- названием рабочей концепции и одной фразой обещания;
- setting depth S0–S4 и связь мира с механикой;
- mascot: NO / BRAND / HELPER / CELEBRATION / PROGRESSION / HERO; роль и сцены;
- палитра, shape/material, иконка, типографика, фон, игровая зона, кнопки, награды;
- **Первый проход:** один сопоставимый gameplay-экран, одна иконка, 3–5 образцов стиля и mascot/no-mascot sheet; **для 1–2 финалистов:** 6 сопоставимых экранов **одних и тех же игровых состояний**, не разный gameplay;
- около 3–5 assets family образцов, 2 event response и короткая motion plan;
- производственная стоимость полного v1, альтернативы более дешёвого производства;
- обоснование узнаваемости, читаемости, риски и ограничения.

**Требование визуального доказательства:** agent должен действительно приложить mockups, renders, PNG/WEBP или real renderer captures для сравнения, когда ему доступны средства создания графики. Если их нет, честно оставить текстовый concept pitch без заявления, что полноценный визуальный выбор сделан. Упоминание «планирую сделать mockups» не закрывает G2.

Все mockups маркировать **CONCEPT / NOT GAMEPLAY**. Видео/GIF из работающего приложения маркировать конкретным build/revision. Не показывать фальшивый игровой прогресс как реально заработанный.

### Step D — trade-off comparison

1. Отсечь hard fails: touchability, читаемость, неоригинальная IP, неподъёмная стоимость, противоречие основному действию.
2. Сравнить прошедшие варианты по [взвешенной матрице](METHOD.md#7-как-сравнивать-без-фальшивой-объективности), назначив веса владельца/объяснив допущения.
3. Для каждой альтернативы назвать **лучшее преимущество**, **самый неприятный компромисс**, **стоимость масштабирования**, **какой риск неопределён**.
4. Показать рекомендацию агента и runner-up, не скрывать, если преимущество тонкое или зависит от вкуса.
5. Сформулировать решение для владельца: **A / B / C / новая итерация**, возможность условного approval («B без героя в HUD»).

### Step E — после решения владельца

Не сразу производить всё:
- собрать vertical slice реального UI, 3 gameplay states, one asset family, touch, animation, safe area;
- сравнить с утверждённым pitch и показать расхождения;
- заполнить [ART_BIBLE_TEMPLATE.md](ART_BIBLE_TEMPLATE.md), зафиксировать revision и owner approval;
- после этого производить серию ассетов, фиксировать master, prompt/provenance, asset budget, runtime size and QA;
- любые изменения setting/mascot/visual pillars должны проходить отдельный brief с причиной, а не «дизайнерский дрейф».

## Обязательный формат ответа владельцу

### В первом отчёте (ещё без выбора)

1. **Текущий смысл игры**: игровое обещание, целевое устройство, сложный экран, чего не знаем.
2. **Что наблюдали у референсов** и какие приёмы можно адаптировать, а что нельзя заключить.
3. **Галерея A/B/C с одинаковыми состояниями**, настройки сеттинга/маскота и отдельные icon tests.
4. **Таблица сравнения** читаемость, узнаваемость, пригодность, production burden, риски.
5. **Рекомендация и почему**, включая отказ от маскота/мира если уместно.
6. **Открытые вопросы только по существенным развилкам**; прочее решить обоснованно.
7. **Чёткий approval gate**: «Предлагаю выбрать вариант B; после утверждения сделаю vertical slice, но не до него».

### Во втором отчёте (после выбора)

- Одна утверждённая Art Bible, со статусом APPROVED / PROVISIONAL.
- Сравнение эталонного pitch и реального рендера.
- Чеклист состояний, 320 viewport, system text, RU/EN, banner, store icon, reduced motion.
- Реальные затраты и remaining risk; список несоответствий, без заявлений о реальном retention uplift.
- Инструкции следующему агенту и запреты на произвольное переизобретение.

## Не делайте

- Не отвечать «концепт B круче» без сопоставимого игрового скриншота.
- Не делать варианты разной насыщенности интерфейсом, если изменяется и игровая механика.
- Не добавлять маскота лишь потому, что он есть у успешной игры.
- Не считать генерацию десяти картинок экономией, если на уровне всего банка будут конфликтовать формы.
- Не путать корпоративного персонажа издателя и персонажа игры.
- Не объявлять approved без решения владельца, особенно для известных пользовательских предпочтений.
- Не переписывать исходные gameplay/storage/ad/analytics API в ходе графического исследования.
- Не переносить конкретный стиль в mini-games-kit как дефолт.
