# Puzzle Design — выборочная методология для игровых проектов

**Статус:** исследовательская база и практические рекомендации, не SDK и не обязательный комплект механик. Снимок корпуса: 11 ноября 2026 года.

**Visual direction and UX preproduction:** отдельная [методология выбора сеттинга, маскота и графического направления](../visual-preproduction/README.md). Она дополняет исследования удовольствия/удержания, но не внедряет механики и не выбирает стиль за проект.

## Специальная диагностика первых минут (не новая обязательная тема)

При доказанной проблеме **первого запуска, понимания правил, самостоятельности или раннего отказа** использовать [FTUE Diagnostic Protocol](FTUE_DIAGNOSTIC_PROTOCOL_2026-11-12.md), затем [FTUE Independent Evidence Audit](FTUE_INDEPENDENT_EVIDENCE_AUDIT_2026-11-12.md). Шаблон [FTUE Playtest Record](FTUE_PLAYTEST_RECORD_TEMPLATE.md) копировать только в соответствующий consumer. Эти документы **дополняют Gate 2 существующего Playbook**; они не меняют подсчёт семи архивных исследований/восьми основных направлений, не вводят onboarding SDK и не требуют всем играм новой обучающей системы.

**30 секунд / 3 минуты / 15 минут — условные окна наблюдения, не обязательные временные нормы.** Прогресс обучения, самостоятельное решение, удовольствие и возврат измеряются отдельно. Отсутствие свидетельств проблемы — HOLD/NO CHANGE.

## Главное правило

**Каждый проект сам выбирает применимые направления.** Перед продуктовой доработкой запишите для каждого рассматриваемого направления **SELECT / HOLD / REJECT**, проблему, свидетельство и способ проверки. За один проход обычно берите **одно–два направления**, а не все восемь. Если подтверждённой проблемы нет, правильное решение — **HOLD: ничего не внедрять**.

Обязательны корректность правил, сохранений, возврата и честность измерений. Необязательны: директоры, дополнительные награды, персонализация, live-ops, новые валюты, усложнение UI. Результат исследования не означает требование добавить функцию.

**Начать здесь:** [Как выбрать направления](PROJECT_SELECTION.md) → [Playbook](PUZZLE_DESIGN_OPERATING_PLAYBOOK_2026-11-11.md) → [Независимый аудит доказательств](INDEPENDENT_EVIDENCE_AUDIT_2026-11-11.md) → [Шаблон записи решения](ADOPTION_RECORD_TEMPLATE.md).

## Карта направлений

| Направление | Когда рассматривать | Когда НЕ внедрять |
| --- | --- | --- |
| **Challenge / adaptive difficulty** | Доказаны неудачные выдачи, провалы ритма, несправедливые тупики | Фиксированное сравнимое испытание, нет диагностики генератора |
| **Experience / causal game feel** | Игрок не чувствует действие, награда нечитаема, нарушен контроль | Уже достаточно ясная и насыщенная обратная связь |
| **Novelty & anticipation** | Повторяются одни и те же типы решений, нет понятного следующего открытия | Добавление контента перегрузит игру; спокойное повторение — часть обещания |
| **Motivation / cross-session** | Трудно вернуться к сохранённому контексту или выбрать следующую задачу | Нет доказательств проблемы; продукт рассчитан на одно завершённое посещение |
| **Mastery / boredom / fatigue** | Игроки освоили правила, но формы задач стали механически идентичными | Не измерены различия стратегий и качество задач |
| **Hidden friction / monetization** | Реклама прерывает действия, ломает возврат, помощь несправедлива | Проблема только гипотетическая; уже действует безопасный контракт |
| **Experimentation** | Есть конкретная спорная гипотеза и контролируемая альтернатива | Нет базовых корректных данных или не определён исход решения |
| **Reverse engineering** | Нужен сопоставимый референс для конкретного UX/пейсинга | Хочется механически копировать функции лидера рынка |

Примечание: восемь тем представлены **семью** исходными исследовательскими отчётами (Experience и Novelty объединены). Отдельные эксперименты, в отличие от игровых функций, — способ проверки гипотез.

## Границы kit

[Интеграция с существующими примитивами](INTEGRATION_BOUNDARIES.md) объясняет, какие механизмы уже реализованы в API и почему игровые политики нельзя переносить автоматически. **Новых директорских runtime-модулей этот пакет не добавляет.** Документация не меняет npm exports, игровой код или поведение существующих проектов.

Исходные исследования и исходный аудит сохранены как датированный корпус, в них могут встречаться устаревшие статусы проектов. Например, владелец уточнил, что «Семечки» **не опубликованы в RuStore и не отправлены на модерацию** — старые тексты репозитория могли утверждать обратное. Перед внедрением сверяйте текущий Git HEAD, статус владельца и реальные доказательства; не считайте исторические числа отраслевыми нормативами.
