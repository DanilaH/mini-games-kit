# Рабочие задания агентам по улучшению шести пазлов

**Версия:** 1.0 · **Основание:** `PUZZLE_DESIGN_OPERATING_PLAYBOOK_2026-11-11.md` и `INDEPENDENT_EVIDENCE_AUDIT_2026-11-11.md`.

> Ни одно из заданий **не требует внедрять все директоры**, создавать универсальный Game Design Framework или публиковать игру. Агент должен сначала проверить актуальный Git HEAD, project-specific решения, уже сделанные изменения и real runtime. Если гипотеза неверна — вернуть обоснованное `HOLD/DROP`, а не создавать изменение ради отчёта. Для задач, которые уже выполняет другой агент, сначала сверить последний handoff и не создавать конфликтующие правки.

## Общий обязательный протокол (копировать в каждое агентское задание)

1. Прочитать Playbook и независимый аудит, затем README / AGENTS / DECISIONS / HANDOFF целевого проекта. **Текущее прямое указание владельца выше устаревшей документации.**
2. До работы записать commit, правила, статус релиза, доступные сценарии запуска, исходный screenshot/video и три наиболее вероятных риска.
3. Проверить потенциальные проблемы на реальном коде/production-browser/записи. Выставить категорию доказательств F/S/O/A/E/G/H.
4. Выбрать **одну основную продуктовую гипотезу** и максимум два независимых P0/P1 исправления. Не объединять эксперимент с изменением рекламы, балансом и метой.
5. Тесты: unit/property, independent oracle где уместен, browser end-to-end, performance/lifecycle, Android по доступности, before/after и авторский review результата. Не заявлять «проверено на физическом телефоне» без такого теста.
6. Обязательно дать вывод `ADOPT / ITERATE / HOLD / DROP`, оценку maintenance, ненайденные доказательства, список сознательно не внедрённых механизмов.
7. Не менять SDK secrets, приложение не отправлять на модерацию, не менять production ad ids и не делать коммиты в `mini-games-kit` без отдельного задания.

## 1. «Семечки» — `DanilaH/seeds-bits`

**Факты:** пользователь подтверждает, что приложение **не опубликовано в RuStore и не отправлено на модерацию**. В репозитории уже зафиксирован пакет 1.1.1 с исправлениями навигации, продолжения тетради, начала обучения и Android notifications. Предварительные AppMetrica отчёты имеют неопределённое происхождение установок, поэтому нельзя называть их публичным retention.

**Приоритетная гипотеза для проверки:** первые 10–15 минут недостаточно ясно связывают базовое удаление пары с понятной следующей самостоятельной целью; длинная Classic может стать механическим перебором. Не считать это дефектом без playtest.

**Тестовые задачи:**

- Холодный первый запуск, две формы обучения, 15 минут Classic, переход в тетрадь, завершение короткой задачи, возврат после background и процесс kill.
- Измерить реальные смысловые моменты: первое самостоятельное удаление, первое добавление цифр, первый тупик, первая подсказка, первый очевидный прогресс и добровольный выход.
- Отдельно проверить, в самом ли последнем коде `game_complete` отправляется до подтверждённого save, и связать `game_start` / `game_complete` одним идентификатором попытки без повторного подтверждения на перезапуске.
- Не менять правила числа, формат сохранения и размер core-поля без отдельно подтверждённой необходимости. Никаких денежных/рекламных причин для скрытого усложнения.

**Готовность:** записаны before/after первого опыта; честно указаны недоступные тесты; корректность save/event инвариантов; нет новой навязчивой меты.

## 2. Блоки — `DanilaH/blocky-block-puzzle`

**Гипотеза:** различия в качестве трёх выдаваемых фигур связаны с количеством разумных продолжений, а не только с доказательством существования решения.

**Тестовые задачи:**

- Сверить актуальность исходных TЗ, Game-kit и реализации Classic. Начинать с кодовой базы, не с фантазии о готовом генераторе.
- Создать offline-запуск парных seeds (контрольная policy и проходимая тройка), несколько ботов с разными эвристиками, ограниченные time/node budgets, independent validator.
- Измерить распределение завершений и ранних проигрышей, `fallback`, «коридор разумных действий», чрезмерно длинные партии и повтор одного способа очистки.
- По результатам выбрать наименьший кандидат для ограниченного человеческого A/B-UX сравнения, **не выпускать скрытый директор ради самого директора**.

**Готовность:** воспроизводимые seeds, одинаковые rules, версии policy, независимые контрольные решения, отдельные цензурированные прогоны, report без утверждения о retention.

## 3. «Стрелки» — `DanilaH/arrows`

**Факты:** банк c05–c120 уже перестроен структурно, UX-review 0.15.0 закрыл ряд экранных проблем. Не переделывать эти задачи автоматически.

**Гипотеза:** рост плотности и dependency depth не всегда совпадает с человеческим ощущением разнообразия/читаемости.

**Тестовые задачи:**

- Выбрать набор маленьких, обычных, Hard/Nightmare полей с разными силуэтами и похожими структурами.
- Сопоставить structural metrics (early freedom, depth, bends, визуальная плотность) с действиями новых пользователей, ошибками и временем до первого полезного удаления.
- Проверить, как срабатывает причинный отклик «убрал одну стрелку → открылась цепочка», не зашумляет ли визуальный эффект следующие ходы.
- Проверить recent UX fixes на 320×568, landscape и native Back прежде новой анимации.

**Готовность:** доказанные контрпримеры структурных метрик, а не новый генератор/мета по умолчанию.

## 4. Сортировка воды — `DanilaH/watery-water-sort`

**Гипотеза:** последовательности переливаний после обнаружения решения могут быть чрезмерно длинными, а награды/анимации не всегда различают осмысленное открытие и механическое выполнение.

**Тестовые задачи:**

- Выбрать 10–15 разных уровней, включающих базовую сортировку и уже существующие модификаторы. Проверить solver/witness и человеческую понятность.
- Разметить подготовительный ход, освобождение буфера, завершающее переливание цвета и количество механических шагов после найденного плана.
- Отдельно проверить undo/hint/recovery, не прерывает ли праздничное переливание следующий ввод.
- Не добавлять новые цвета, сосуды, валюты или правила прежде подтверждения существующего дефицита вариативности.

**Готовность:** human/solver distinction, независимые ошибки/тупики, measured timing и небольшой policy candidate или обоснованный HOLD.

## 5. «Дороги» — `DanilaH/road-lines`

**Факты:** существует банк 90 задач и отдельный `MONETIZATION_PLAN.md`. Значения ad caps — локально принятое продуктово-техническое решение, не научный оптимум.

**Гипотеза:** часть уровней визуально различна, но не заставляет игрока открывать новый маршрутный приём; лишние переходы/предложения после победы могут быть дороже их мотивационной пользы.

**Тестовые задачи:**

- Пометить семейства решений; сравнить реальные пути через различные 2–3 правила, зафиксировать все заведомо различающиеся контрпримеры.
- Снять победу → награда → переход → следующий уровень в production-браузере, а при возможности на телефоне. Измерить реальное wait/control delay, не только анимационный duration.
- Проверить no-fill, fail-close и продолжение без объявления в соответствии с действующим рекламным ТЗ.
- Не возвращать отклонённые x5/rewarded wheels или новые meta layers только потому, что они встречались у конкурентов.

**Готовность:** доказанный UX-effort gain или честное отсутствие проблемы при текущем дизайне.

## 6. Солитёр ассоциаций — `DanilaH/asoc-solitair`

**Факты:** актуальная документированная версия 0.9.1; все 33 предметные иллюстрации уже приведены к более простому casual-языку. Не использовать как основание устаревшую жалобу на перегруженный барабан без нового теста.

**Гипотеза:** некоторые ассоциации неочевидны из-за содержания категорий/иконок, а не из-за математической сложности; настоящую награду даёт самостоятельный «ага-момент».

**Тестовые задачи:**

- Снять первую холодную партию, открытие/сбор группы, неверные семантические предположения, подсказку и возврат.
- Слепой редакторский тест предметных карт: узнаваемость на игровом размере и однозначность соответствия категории; исключить наводящие подписи.
- Проверить, что помощь указывает на действие, но не решает всё за игрока, и что раскрытие карты не задерживается из-за чрезмерного эффекта.
- Не менять frozen saved deals и content IDs без миграционного плана.

**Готовность:** конкретные неоднозначные пары с доказательством, независимый тест макета и никакой «магической» персонализации.

## Финальная форма handoff для всех агентов

1. `BASELINE.md`: версия, доказательства, список подтверждённых проблем и неподтверждённых гипотез.
2. `EXPERIMENT.md`: один основной вопрос, alternatives, критерии успеха/провала, guardrails, проектные costs.
3. `CHANGES.md`: что реально изменено, где, почему и как откатить.
4. `EVIDENCE/`: настоящие записи/screenshots, тесты, seeds/fixtures, логи только без секретов/PII.
5. `FINAL.md`: Adopt/Iterate/Hold/Drop, список рисков и ещё не выполненных проверок.

**Главная проверка:** продукт стал лучше для игрока или просто сложнее внутри кода? Если доказательств первого нет — не объявлять успех.
